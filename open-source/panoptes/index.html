Panoptes

Panoptes by PCGsoft is a local, browser-based control centre for a self-hosted AI workstation: live hardware and inference telemetry, engine profile switching with automatic rollback, and agent job history.

Last reviewed 20 November 2026

Active development

Everything described below is implemented in the public source and runs on Linux. There is no hosted instance and no public URL: Panoptes listens only on the machine it watches.

What is Panoptes?

Panoptes is a dashboard for one self-hosted AI development workstation. One small Python server (standard library only, no build step and no CDN) serves a plain HTML, CSS and JavaScript interface that reads local hardware sensors, local inference engines, local agent-harness records and the supervisor's job history. It is administered in a browser on that same machine.

What does it do today?

  • Hardware — CPU load and clocks, memory and swap, storage I/O, and per-GPU utilisation, temperature, power, clocks and PCIe link path.
  • Inference — one section per configured engine behind per-type adapters (Radiance, llama.cpp, OpenAI-compatible): model and state, decode versus effective throughput, latency histograms, queue depth, speculative decoding and KV-cache figures, each shown only when the engine advertises it.
  • Engine profiles — preview a candidate profile against the active one, apply it after an explicit confirm, watch the restart step by step, and roll back automatically if the engine does not come back serving the new profile. Only approved parameters can change, the model identity is locked and every switch is journalled with a manual restore.
  • Container controls — status, logs, start, stop and restart of the configured engine, each confirmed twice and refused by a root helper while a supervised task is running or requests are in flight.
  • Agent telemetry — live worker state from a local agent harness (OMP today) plus job history with duration, tokens, cost and energy per task, every value tagged with its provenance and exportable as a redacted Markdown report.
  • Lab — read-only comparison of one benchmark variant against another, with run-to-run noise handled explicitly, per-task trends marked at configuration changes, and Markdown report export.

What is read-only and what can change things?

Browsing is read-only: it reads sensors, engine status endpoints and local files. The only state-changing actions are container start/stop/restart and profile apply or restore. Each is POST-only, needs a per-launch token and an explicit confirmation in the page, and goes through the same guarded root helper.

What about data the machine does not expose?

A reading the machine does not expose is reported as unavailable, never as zero, and derived figures are marked as calculated rather than measured. Exported reports redact home-directory paths and secret assignments, and state how many redactions were made.

An engine adapter is not a benchmark.

Panoptes reports what an engine advertises about itself. Throughput and latency figures are that engine's own numbers, shown with their provenance, not a PCGsoft performance claim.

Privacy and locality

Nothing leaves the machine.

Why is there nothing to try online?

Panoptes binds to the loopback interface only and has no hosted instance, no account and no public URL. It monitors the machine it runs on, so there is no remote demo and nothing to sign up to; you install it and open it in your own browser. The server prints its own loopback address on startup.

What stays on the machine?

  • Configured engine base URLs are validated to be loopback; a non-loopback entry is skipped with a warning rather than contacted.
  • Agent-harness telemetry is counts only — tokens, compactions and tool calls — never message text.
  • Hardware, inference, job and lab data are read locally and rendered locally; there is no upstream reporting endpoint.
  • Sending telemetry out of the machine is deliberately out of scope, not merely unfinished, along with a build step, third-party front-end dependencies and any publishing automation.

Roadmap

Not implemented, and not presented as available.

  1. Panoptes Guardian: hardware protection and emergency stop built on the interlocks the container controls already use.
  2. Multi-GPU discovery on headless servers.
  3. Windows and macOS support; the current source is Linux only.
  4. Agent harnesses beyond OMP.

Where the rough edges are: the data path is the mature part of the project — readings are either real or marked unavailable. Engine coverage and interface polish are still developing.

Running it

Standard-library Python, no build step.

Linux only.

The backend is Python 3.12 standard library with no pip installs; the interface is plain HTML, CSS and JavaScript with no npm and no CDN. The Python suite runs on unittest and the pure-JavaScript tests on Node's built-in test runner.

The repository also documents the optional root components, the release scan and the rollback procedure for every change the project can make to a machine.

FAQ

Can I try Panoptes without installing it?

No. There is no hosted instance and no public URL: the server listens on the loopback interface of the machine it monitors.

Does Panoptes send any data off the machine?

No. It binds to the loopback interface only, refuses non-loopback engine URLs, and sending telemetry out of the machine is out of scope by design rather than an unfinished feature.

Does it read AI agent conversations?

No. Harness telemetry is counts — tokens, compactions and tool calls — never message text, and exported reports redact home-directory paths and secret assignments.

Does it run on Windows or macOS?

Not today. The current source is Linux only; Windows and macOS support is on the roadmap.

Is Panoptes Guardian available?

No. Guardian hardware protection and emergency stop are roadmap work built on the interlocks that the existing container controls already use.
